# Loop: поэтапное внедрение функционала «Класс» (Vue + Supabase)

Этот файл — управляющий промпт (loop) для AI-агента по реализации функционала
«Класс» из `Промпт для разработки страницы Класс.docx`. Агент выполняет фазы
**строго последовательно**, проверяет Definition of Done (DoD) каждой фазы, и
**только при выполнении DoD** переходит к следующей. Если DoD не выполнен —
фаза дорабатывается, проект не «коммитится» и не переходит дальше.

---

## Как пользоваться этим loop

1. Прочитай `Промпт для разработки страницы Класс.docx` и этот файл целиком.
2. Найди блок **ТЕКУЩЕЕ СОСТОЯНИЕ** внизу файла. Если он пуст — начинай с Фазы 1.
3. Выполни только текущую фазу (контекст → задачи → файлы → код → проверка).
4. Запусти проверки из блока «Проверка» фазы. Если упали — чини, не уходи дальше.
5. Заполни DoD фазы. Обнови **ТЕКУЩЕЕ СОСТОЯНИЕ**: `phase: N+1`, добавь что сделано.
6. Повтори, пока не пройдёшь все фазы.
7. В конце запусти Фазу 6 (QA) и обнови `status: DONE` только если все пункты пройдены.

Правила:
- Не делай «на будущее» то, что не входит в задачи фазы.
- Соблюдай конвенции репозитория (см. `src/`, `supabase/`).
- Не коммить без явной просьбы пользователя.
- Команды проверки берутся из `package.json` (lint/typecheck/build/test). Если их
  нет — сначала добавь минимальный скрипт проверки в рамках текущей фазы.

## Зафиксированные решения (UX spec, Этап «Уточнение UX»)

Алгоритм присоединения (исправленный, подтверждён пользователем):
- «Присоединиться к классу» открывает модалку.
- Пользователь вводит **4-значный код комнаты** и нажимает «Проверить».
- Система проверяет существование комнаты по ключу (RPC `get_room_info`,
  SECURITY DEFINER — т.к. ученик не видит чужие комнаты из-за RLS) и показывает
  её название.
- Если комната найдена, пользователь **подтверждает** добавление своего
  **текущего скетча**; только тогда вызывается `join_room_by_key` и создаётся связь.
- «Текущий скетч» — это скетч, открытый/сохранённый в редакторе; его id берётся из
  `localStorage['p5editor_current_sketch_id']`. Если его нет — показываем подсказку
  «сначала откройте и сохраните скетч в редакторе».
- Сообщение «Ваш скетч присоединен к комнате <Название комнаты>» показывается на
  странице «Класс» под верхним меню после успешного `join_room_by_key` (banner).
- Страница «Класс» доступна **всем авторизованным** пользователям (ученик и учитель).
- Один скетч → только одна комната (`unique(sketch_id)` в `room_sketches`).

> ВНИМАНИЕ: добавлен RPC `get_room_info` — его нужно применить в Supabase
> (дополнение к секции 13 миграции), иначе проверка комнаты не сработает.

## Фаза 1 — Backend / Supabase foundation

**Контекст.** База уже есть (папка `supabase/`). Нужно добавить таблицы комнат и
связей, расширить `sketches`, настроить ограничения, RLS и RPC-функции.

**Задачи.**
1. Миграция: создать `class_rooms` (id uuid PK, owner_id uuid → auth.users,
   title text, description text, room_key text unique, created_at, updated_at).
2. Миграция: создать `room_sketches` (id uuid PK, room_id → class_rooms,
   sketch_id → sketches, student_id uuid → auth.users, rating int default 0,
   created_at, updated_at).
3. Расширить `sketches`: добавить `numeric_sketch_id` (bigint или text, unique),
   `status` (text, default 'saved').
4. Constraints: `class_rooms.room_key` ~ `^\d{4}$` + unique; `room_sketches`
   `unique(sketch_id)`; `rating between 0 and 4`; `numeric_sketch_id` unique.
5. RLS:
   - `class_rooms`: owner видит/создаёт/обновляет/удаляет только свои (USING/CHECK `owner_id = auth.uid()`).
   - `room_sketches`: владелец комнаты видит/удаляет/меняет рейтинг; ученик
     создаёт связь только для `student_id = auth.uid()` и своего скетча.
   - `sketches`: пользователь управляет своими; учитель читает скетчи своей комнаты
     через `EXISTS (select 1 from room_sketches rs join class_rooms cr ...)`.
6. RPC-функции (SECURITY DEFINER, где нужно обойти RLS корректно):
   - `create_room(title, description)` → генерит уникальный 4-цифровой `room_key`
     (loop с retry при коллизии unique), возвращает row.
   - `join_room_by_key(p_room_key, p_sketch_id)` → транзакционно: проверяет
     комнату, что скетч принадлежит `auth.uid()`, что скетч ещё не привязан,
     допустимый статус; создаёт связь; возвращает `room_title`.
   - `remove_sketch_from_room(p_room_sketch_id)` → удаляет только связь.
   - `update_room(p_room_id, p_title, p_description)` → только владелец.
   - `update_room_sketch_rating(p_room_sketch_id, p_delta)` → `rating` в `0..4`.

**Файлы.** `supabase/migrations/<ts>_class_rooms.sql`,
`..._room_sketches.sql`, `..._sketches_ext.sql`, `..._class_rls.sql`,
`..._class_rpc.sql` (или один общий миграционный файл в стиле репозитория).

**Проверка.**
- Применить миграцию локально (`supabase db reset` / `supabase migration up` либо
  через SQL-клиент к dev-проекту).
- Ручной smoke-тест RPC: создать комнату, проверить формат/уникальность `room_key`;
  join валидного/чужого/уже привязанного скетча; коллизия ключа обрабатывается.
- RLS: попытка прочитать чужую комнату другим пользователем → 0 строк.

**DoD.** Таблицы созданы; constraints и FK работают; RLS настроен; все 5 RPC
протестированы вручную; коллизии `room_key` и `numeric_sketch_id` обрабатываются.

## Фаза 2 — Интеграция скетчей (save / URL / Explore)

**Контекст.** Существующий редактор/сохранение скетчей нужно доработать под
`numeric_sketch_id`, статус `saved`, URL с ID и исключение из «Исследуй».

**Задачи.**
1. При сохранении скетча: присвоить `numeric_sketch_id` (генерация + retry при
   коллизии unique), выставить `status = 'saved'`.
2. URL редактора/просмотра скетча содержит `numeric_sketch_id`
   (напр. `/sketch/:numericSketchId`), ID виден в адресной строке.
3. Личный кабинет: показывать `saved`-скетчи со статусом «сохранён», помечать,
   прикреплён ли уже к комнате.
4. Страница «Исследуй»: исключить выборку `status = 'saved'` (показывать только
   опубликованные/публичные).
5. Открытие скетча по цифровому ID работает (editor + readonly viewer).

**Файлы.** Места сохранения скетча (`src/...`), роуты скетча, кабинет,
компонент «Исследуй», поиск/выборка в Supabase-клиенте.

**Проверка.** Сохранить скетч → в БД `numeric_sketch_id` + `status='saved'`,
URL меняется; в кабинете виден, в Explore — нет; открывается по цифровому ID.

**DoD.** Скетч сохраняется с цифровым ID; ID в URL; не попадает в Explore; виден
в кабинете как saved; открывается по ID.

## Фаза 3 — Frontend: страница «Класс» (`/class`)

**Контекст.** Основной экран со списком комнат, созданием, join и баннером успеха.

**Задачи / файлы.**
- Роут `/class` (при необходимости auth guard).
- `src/pages/ClassPage.vue` (или `views/`), `RoomsTable.vue`, `RoomRow.vue`,
  `CreateRoomModal.vue`, `JoinRoomModal.vue`, `JoinSuccessBanner.vue`.
- Composable `useClassRooms()` с `fetchRooms/createRoom/deleteRoom/joinRoom/searchRooms`.
- Верхняя панель: «Создать комнату», «Присоединиться».
- Баннер «Ваш скетч присоединен к комнате <room_title>» (скрыт по умолчанию).
- Поиск по названию/описанию/ключу (debounce).
- Таблица колонок: открыть, название, ключ, описание, дата изменений,
  кол-во скетчей, удалить (с confirm).

**Поведение.** create → обновить таблицу; join → banner с `room_title`; delete →
confirm + обновление; search фильтрует.

**Edge cases.** нет комнат; ключ не найден; скетч уже привязан; нет подходящего
saved-скетча; не авторизован.

**Проверка.** `npm run lint && npm run typecheck && npm run build`. Запустить
dev, проверить сценарии вручную.

**DoD.** Список грузится; поиск работает; комната создаётся/удаляется; join по
ключу работает; баннер успеха показывается.

## Фаза 4 — Frontend: страница «Комната» (`/class/:roomId`)

**Контекст.** Управление конкретной комнатой: список скетчей, preview, рейтинг.

**Задачи / файлы.**
- Роут `/class/:roomId`.
- `RoomPage.vue`, `RoomHeader.vue`, `RoomSketchList.vue`, `RoomSketchListItem.vue`,
  `SketchPreviewPane.vue`, `RatingControl.vue`.
- Composable `useRoom(roomId)` с `fetchRoom/updateRoom/fetchRoomSketches/
  selectSketch/removeSketchFromRoom/changeRating`.
- Верх: «Назад», название, описание (editable), «Сохранить».
- Лево: preview выбранного скетча + «Открыть в редакторе» (новая вкладка по
  цифровому ID).
- Право: список — «Посмотреть», название, имя пользователя, «Удалить из комнаты»,
  звёзды 0..4, `+`/`-`.

**Поведение.** «Посмотреть» грузит preview слева; «Открыть в редакторе» — новая
вкладка; «Сохранить» пишет title/description; «Удалить из комнаты» — только связь
+ очистить preview если нужно; рейтинг `+` до 4, `-` до 0 (save сразу/debounce).

**Проверка.** `npm run lint && npm run typecheck && npm run build`; ручной прогон.

**DoD.** Страница открывается; список грузится; видны имя пользователя и рейтинг;
preview работает; удаление из комнаты работает; рейтинг меняется; metadata
комнаты сохраняется.

## Фаза 5 — Интеграция join-сценария (связка Фаз 2–4)

**Контекст.** Соединить «Присоединиться» из контекста saved-скетча с
`join_room_by_key` и баннером.

**Задачи.**
1. В `JoinRoomModal` определить активный saved-скетч (из сост. приложения/выбора).
2. Вызвать `join_room_by_key(room_key, sketch_id)`; при успехе показать баннер с
   `room_title`; при ошибке — понятное сообщение (неверный ключ / уже привязан).
3. Запретить повторное присоединение того же скетча (проверка на клиенте + RPC).
4. В кабинете помечать «прикреплён к комнате <title>».

**Проверка.** Сквозной сценарий: ученик сохраняет скетч → «Присоединиться» →
ввод ключа → баннер; повтор → ошибка.

**DoD.** Join из контекста скетча работает; баннер корректен; повтор блокируется.

## Фаза 6 — QA и полировка

**Контекст.** Проверка логики, доступов, UX.

**Тест-кейсы.**
- Комнаты: создание, уникальный 4-значный ключ, таблица, поиск, удаление.
- Присоединение: валидный ключ → скетч привязан + баннер; неверный ключ → ошибка;
  уже привязанный → блок.
- Комната: список, имя пользователя, «Посмотреть», «Открыть в редакторе»,
  «Удалить из комнаты», рейтинг 0..4.
- Скетчи: saved в кабинете; saved не в Explore; numeric ID в URL.
- Техника: RLS блокирует чужие комнаты; RPC join не пускает чужой скетч; unique
  и коллизии обрабатываются.

**UX-полировка.** загрузчики на кнопках; empty states; сообщения успех/ошибка;
disabled-состояния; debounce поиска; адаптив (по необходимости).

**Проверка.** `npm run lint && npm run typecheck && npm run build && npm run test`
(если есть e2e — запустить smoke-тест).

**DoD.** Все функциональные и технические кейсы пройдены; UX-полировка выполнена.
